## Solution :

This one's all about digging through git history. Even if a file looks "clean" right now, every previous version of it is still sitting in the `.git` folder, and `git log` lets us dig through that. This article was a good refresher on how git actually works under the hood: https://jwiegley.github.io/git-from-the-bottom-up/

We start by cloning the repo and checking out `README.md`, where the password field is redacted with `xxxxxxxxxx`. So the actual password isn't sitting there in plain sight — but it might still be in an older commit.

Running `git log` shows three commits, and the most recent one is suspiciously titled **"fix info leak"** — basically a confession that something sensitive got removed here.

To see *exactly* what changed in that commit, we use `git log -p`, which shows the diff (patch) for every commit in the history:

> Lines starting with `-` are content that existed before and got removed, lines starting with `+` are what got added in its place.

And sure enough, in the "fix info leak" commit's diff, we can see the real password getting swapped out for `xxxxxxxxxx`:

```diff
- password: 4pT1t5DENaYuqnqvadYs1oE4QLCdjmJ7
+ password: xxxxxxxxxx
```

> The big takeaway here: just overwriting a secret and committing the change does **not** actually delete it from git history. The old commit — and the old password — is still fully intact and recoverable via `git log -p`. To truly scrub a secret from a repo, you'd need to rewrite history entirely (e.g. `git filter-branch` or tools like `bfg-repo-cleaner`).

## Solution :

This level builds on the tag stuff from Bandit30, but now we actually need to push something to the remote repo. The README says we need to push a file called `key.txt`, containing exactly `May I come in?`, to `master`.

First roadblock: the repo has a `.gitignore` containing `*.txt`, so a normal `git add key.txt` just silently does nothing — git won't track it at all, which leads to confusing "nothing to commit" messages even though the file clearly exists.

Along the way there were a few failed attempts too — pushing files with the wrong name/content (like `testtt.txt`, or a file literally named `touch`), and at one point pushing without actually committing first. All of these got rejected by the remote's pre-receive hook — a validation script the server runs *before* accepting a push.

To clean things up, we ran `git reset --hard origin/master` to wipe out our messy local commits and resync to exactly what the server has.

From there:
1. Created the correct file: `echo "May I come in?" > key.txt`
2. Force-added it despite `.gitignore`: `git add -f key.txt` — the `-f` flag is what overrides the ignore rule.
3. Committed normally and pushed.

This time the pre-receive hook validated the file's content and printed the password for the next level.

> A few things worth remembering from this one:
> - `.gitignore` can silently block `git add` — if a file won't stage no matter what, check for ignore rules, and use `-f` to force it through if needed.
> - Pre-receive hooks are server-side scripts that can inspect and reject a push before it's accepted — `git push` succeeding locally doesn't always mean the remote actually took it.
> - `git reset --hard origin/<branch>` is the quickest way to throw away local mess and sync back to a known-good state from the remote.

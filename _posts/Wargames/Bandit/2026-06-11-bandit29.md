## Solution :

This one builds on the git skills from Bandit28, but the trick here is different — the password isn't hiding in old commits on `master`, it's hiding on a completely different branch.

We start by cloning the repo and checking `README.md` on `master`, which just says `<no passwords in production!>` instead of an actual password. So we try the Bandit28 approach first — `git log -p` and `git blame` — to see if an old commit leaked the real password. No luck: the only change in history is a username fix from `bandit29` to `bandit30`, the password line itself was never touched on this branch.

So if it's not in the history of `master`, maybe it's sitting in a different branch entirely. Running `git branch -a` shows all branches, including remote ones we haven't checked out yet:

> When you clone a repo, you only get `master` checked out locally by default — but git still knows about other remote branches (`remotes/origin/...`), you just need to `git checkout <branch>` to actually switch your working files to that branch's version.

This reveals two branches we didn't know about: `dev` and `sploits-dev`. We check `sploits-dev` first — same placeholder password, no luck. Then we check `dev`, and `cat README.md` there shows the real password.

> Makes sense in hindsight — "production" branches tend to get cleaned up, but dev/staging branches often still have leftover credentials, debug notes, etc. that never got scrubbed.

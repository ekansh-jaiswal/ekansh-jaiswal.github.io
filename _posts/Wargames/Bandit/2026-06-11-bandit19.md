> Pass : cGWpMaKXVwDUNgPAVJbWYuGHVn9zl3j8
{: .prompt-info }

## Solution :

This level gives us a SetUID binary (`bandit20-do`) which runs whatever command we pass it as the user **bandit20** instead of bandit19. Since the password file for bandit20 isn't readable by us directly, we just need to get this binary to `cat` it for us.

A couple of failed attempts happen along the way in the transcript — passing the file path directly or just `help` doesn't work, since the binary actually runs things through `env`, and `env` itself doesn't have permission to read the file as bandit19. The fix is simple: just give it a proper command (`cat /etc/bandit_pass/bandit20`) and let the SetUID binary run *that* as bandit20.

### Bash Transcript :

```bash
bandit19@bandit:~$ ls
bandit20-do
bandit19@bandit:~$ ./bandit20-do
Run a command as another user.
  Example: ./bandit20-do whoami
bandit19@bandit:~$ file /etc/bandit_pass/bandit20
/etc/bandit_pass/bandit20: regular file, no read permission
bandit19@bandit:~$ ./bandit20-do "/etc/bandit_pass/bandit20"
env: ‘/etc/bandit_pass/bandit20’: Permission denied
bandit19@bandit:~$ ./bandit20-do help
env: ‘help’: Permission denied
bandit19@bandit:~$ ./bandit20-do whoami
bandit20
bandit19@bandit:~$ file bandit20-do
bandit20-do: setuid ELF 32-bit LSB executable, Intel 80386, version 1 (SYSV), dynamically linked, interpreter /lib/ld-linux.so.2, BuildID[sha1]=d9b51170e04af1b03902f80228afa7a973330f86, for GNU/Linux 3.2.0, not stripped
bandit19@bandit:~$ ./bandit20-do cat /etc/bandit_pass/bandit20
0qXahG8ZjOVMN9Ghs7iOWsCfZyXOUbYO
bandit19@bandit:~$
```

> `whoami` confirms the binary actually runs as bandit20 — that's the SetUID bit in action (the `s` in the file's permission bits, also visible via `file` showing it as a "setuid ELF" executable).

> Once we know it runs as bandit20, running `cat /etc/bandit_pass/bandit20` through it gives us a file read with bandit20's permissions, bypassing our own lack of access.
